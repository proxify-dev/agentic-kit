# Instruction surfaces: which file or hook holds which line

Which file or hook should hold a line, and how to fix one that has gone wrong. Elsewhere:
- [Checking which agent a channel reaches](channels.md)
- [Moving a rule that must always hold into a check](checks.md)
- [Choosing the words of the line](../../context-engineering/SKILL.md)
- Back to [placing a rule](../SKILL.md)

A surface is any place an agent reads instructions from: a CLAUDE.md, a SKILL.md, a hook's injected text, a subagent's brief, a command's output. The agent reading it remembers nothing from the last session, sees only what is loaded, carries every always-loaded line in its context window, and acts on whichever of two copies it reads first.

## The surfaces and what each costs

| surface | loads | costs |
|---|---|---|
| CLAUDE.md chain, `.claude/rules/*` without `paths:` | whole, at launch | every turn of every session in the folder |
| `.claude/rules/*` with `paths:` | whole, when a matching file is read | only sessions that touch those files |
| skill listing | name and description, every turn; cut at 1,536 characters, dropped past about 1% of the context window | every turn, so the description is the budget |
| skill body, reference | when invoked or read | only the turn that needs it |
| agent file | its body is that agent's prompt; `skills:` preloads those bodies whole | every run of that agent |
| output style, `--append-system-prompt` | `system`, the whole session | every turn |
| auto memory | the index lines; topic files when read | the index, every turn |
| MCP server instructions | at connect; cut at 2,048 characters | every turn the server is connected |
| text a hook injects | when its event fires | only when that tool call or event happens |
| a command's output | when the command runs | only after that call |
| a file the agent reads | as a tool result | once; read as data, not as an instruction |

## Levels

Place each fact by how often it is needed, against what it costs to load it every time:

    ALWAYS LOADED     every session, always true, short    in context from the start
    AT THE TOOL CALL  when one kind of tool call happens   a hook's context on that call, a command's output, a check's message
    WHEN NEEDED       inside one task                      behind a link, read when the task needs it
    IN THE CODE       the code and its files               read when working on them

Every request carries the system prompt, the CLAUDE.md chain, each skill's name and description, and every `@`-import. A plain markdown link adds one line; the file behind it adds nothing until it is read. Use the link unless the content must load every time: decide by how often it is needed, not by how important it seems.

## Which lines should be always loaded

A line stays always loaded only if the agent goes wrong without it, and:
1. It tells the agent when or where to act, not what something is.
2. It stays true at this level: a lasting rule, not this week's status.
3. It is worth its cost: every session loads it.
Otherwise move it to a level that loads less often.

An always-loaded file links to the detail; it never repeats what the linked file says. A line that explains uses up the budget and becomes a second copy.

Adding instructions makes the agent follow all of them a little worse, not only the newest (HumanLayer). The numbers in published reports (150-200 instructions, a root file under 60 or about 100 lines) are not proven; the cause is: every added line makes the others a little less likely to be followed.

## The root file is a table of contents

- The root CLAUDE.md or AGENTS.md lists where the docs are; it is not the docs: OpenAI keeps about 100 lines pointing into a structured `docs/` tree, after "one big AGENTS.md" failed in predictable ways.
- Write it by hand and keep only what applies to every task; agent files generated by an LLM were reported to hurt and to cost more (a study relayed by HumanLayer, unverified).
- Grow it one line at a time, each line added because an agent made a mistake without it; drop what a newer model no longer needs. A setup copied from another repo brings rules that contradict or repeat each other (Fowler).

## A rule about an action goes in the message of the check that catches it

A rule that applies when the agent does something goes in the message of the check that catches it: the block, the lint or the refusal names what is missing and how to fix it. It adds nothing to the context window until the action happens, and the agent reads it right after the mistake (forge-harness writes the rule into the blocking message the same way). The always-loaded file keeps only the goals; [building the check](checks.md).

## Keep these files up to date with code

- A check after every write of an instruction file: its length, links that do not resolve, an AGENTS.md that Claude will not read.
- A scheduled sweep for outdated docs, broken links and duplicated rules, opening fixes (OpenAI runs a recurring agent for this).
- A test for each injected text's size and wiring, and one that runs every plugin's SessionStart hooks together.

## CLAUDE.md and AGENTS.md

- Claude Code reads AGENTS.md on its own (v2.1.277+) only when no CLAUDE.md or CLAUDE.local.md sits at or above the folder; otherwise only through an `@AGENTS.md` import. With both: the shared lines go in AGENTS.md, and CLAUDE.md is `@AGENTS.md` plus the lines only Claude needs.
- Everything in CLAUDE.md is read as an instruction by every session in the folder: a finding, a status or the steps of one task written there become instructions. What happened goes to memory ([what goes in a file instead](state.md)).
- A rule a plugin injects stays in the plugin: a copy in CLAUDE.md goes out of date.
- A subfolder's rule goes in a CLAUDE.md in that subfolder, loaded only there.

## Links

- Every link works today: check a link's target exists before writing it.
- When a fact changes, fix every link to it in the same change.
- A known mistake is written down where the next agent will need it, visible there, written for that agent.

## Common problems

| problem | how to spot it | fix |
|---|---|---|
| one file covers many topics | many concerns written inline | link out to separate files; keep what passes the test above |
| lasting rules and short-lived facts at the same level | a lasting rule written next to this week's status, as if equally important | separate lasting rules from current status; status goes to memory |
| a dated status block read as a lasting rule | a "Situation (date)" block | move it to memory |
| a link to the wrong place | points at a moved file, or elsewhere for a fact that is written here | fix or delete the link |
| the same fact in two files | repeats what the linked file says | delete the copy, link to the original |
| a line added for each finished task | the file reads like a work log | write when a fact changes, never after each task |
| extra text around the instructions | frontmatter, headings, a reason or a history around text an agent reads | keep only the instructions; the reason goes in the commit |
| text that assumes the reader was there | "as we discussed", a pronoun with nothing it refers to | write it for an agent with no prior context |
| rules copied from another repo | rules that contradict or repeat each other | keep only the rules added after a mistake here |
| a rule that must always hold, written only as text | broken again and again | [move it to the check that blocks the action](checks.md) |

Fix duplicated facts and wrong links first (the agent acts on wrong information), then the mixing of lasting rules and status.
